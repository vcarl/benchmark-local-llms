# Tool-call evaluation suite

> Design record (2026-11-19). Not maintained; current behavior is in [docs/](../../) — see [SCORING.md § `tool_calls`](../../SCORING.md#tool_calls).

The `toolcall` challenge measures native tool calling: given a catalog of tools as JSON Schema and a request, does the model emit the right calls, with the right arguments and types, or decline when it should. Items are generated by `scripts/author/next/toolcall.ts` and scored by our own deterministic check, `tool_calls`. The Berkeley Function Calling Leaderboard (BFCL v4, commit `6ea5797`) is inspiration and calibration only: its statistics set the generator's bands and some of its function schemas fill out our catalogs, but no BFCL question or answer key is an item.

## Prompt mode

Tools are inline in the prompt as JSON Schema; the answer is a JSON array of `{"name", "arguments"}` calls, or `[]` when no tool fits or a required value is missing. The request shape, archive and digests are unchanged. Sending tools through the runtime's tools API (native mode) is a separate change.

## The `tool_calls` check

A constraint check beside `json_matches`, so multi-turn turns, errata, re-scoring and failure kinds work unchanged. The key lists the expected calls; each argument is a bare value or `{ oneOf: [...] }`, `optional` maps unstated optional arguments to their declared defaults, and `unordered` names array arguments compared as multisets. Calls match as a multiset by a full assignment search (never greedy). There is no global string normalization and no type coercion. An item scores 1 on a full match, 0.75 when the only departure is optional arguments passed explicitly at their defaults (`nearMiss: explicit-default`), and 0 otherwise. Unparseable output scores 0 as `no_answer` and is never a correct abstention. Full rules: [SCORING.md § tool_calls](../../SCORING.md#tool_calls).

## Behaviours and families

60 families × 4 seeds = 240 items; a family is one scenario template, the cluster for the standard error.

| Behaviour | Families | What varies by seed |
|---|---|---|
| single: one call; types, nested objects, arrays, optionals and defaults | 12 | values, which optionals the request states, catalog size; seed 3 is non-English where the op has a translation |
| choice: the target among its near-duplicate siblings | 12 | values, catalog size from the BFCL live_multiple distribution; seed 3 has 12–20 tools |
| parallel: one tool, 2/3/2/4 calls | 8 | 5 families share all but one argument across calls (overlapping values), 3 draw each call independently |
| parallel + multiple: 2–4 calls over 2–3 tools | 8 | seeds 2–3 repeat a tool with fresh values |
| abstention: no tool fits, a required value is missing, the domain's tools cannot do the operation | 4 + 4 + 4 | values, catalog |
| multi-turn: 3–4 turns over one stateful scenario | 8 | values and tool results |

Multi-turn items use gold history: each turn sees the earlier turns' requests and gold calls, and the tool results of the previous turn rendered as text in the next user message. Each turn is scored on its own through the `Turn` machinery, so errors do not compound. Three scenarios withhold a tool for one turn (the gold answer is `[]`) and announce it in the next, which must then call it. 32 multi-turn items yield 108 scored turns; the suite has 316 scored units.

## The screen

Every key is correct by construction. For each gold call, exactly one catalog tool accepts its arguments (strict types and enums), every string and number value is stated in the conversation (the request, earlier requests and tool results; never the schemas), no optional argument is set to its default, and no two calls coincide. Abstention catalogs exclude the request's domain (and related ones), and general-purpose tools (web search, raw HTTP) never fill a catalog. Every item carries its gold answer, plausible wrong answers (missing, duplicated or retyped calls, stringified arguments, sibling tools, guessed values) and an explicit-default near miss where one exists; `sets.test.ts` checks each against the real scorer.

## Catalog and calibration

Catalogs combine 45 hand-written tools across 11 domains (`toolcall-catalog.ts`; each API keeps one naming style) with 52 schemas vendored from BFCL live (`toolcall-vendored.json`; 50 used as filler after dropping two general-purpose tools). Each vendored entry records its source row id and the fixes made on the way in: conversion to our JSON Schema subset, type/enum mismatches, and defaults outside their enum. `NOTICE` names the source; the possible CC BY-SA 4.0 upstream of the Schema-Guided-Dialogue-style schemas is unverified.

`PROFILE` in `toolcall.ts` holds the bands from BFCL live statistics, and `toolcall.test.ts` asserts the generated catalogs stay inside them:

| Statistic | Band |
|---|---|
| tools per item | median 3–4, p90 ≥ 6, at least 4 items with ≥ 12 |
| parameters per function | mean 3.3–4.2, max ≥ 7 |
| required / with default | 50–65% / 35–50% |
| enum / boolean / array / object | 15–20% / 8–12% / 5–8% / 2–4%, depth ≤ 2 |
| function / parameter description, median chars | 80–130 / 50–90 |
| non-English requests | 5–10% (Spanish, French, German) |
| naming styles (snake, dotted, Schema-Guided-Dialogue, camel) | each ≥ 5% of functions shown |

## Errata

`toolcall` is a pre-release (draft) suite. Errata apply only to items of a frozen release, so its items change freely until a release freezes them.

## Deferred

- Native tools-API mode (request shape, digest preimage, tool-role history).
- World-knowledge and relative-date values with `oneOf` alternatives; the generator states every value verbatim.
- A re-authored BFCL live sample as an external-validity probe outside releases.
