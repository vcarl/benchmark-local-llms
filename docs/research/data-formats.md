# Data formats: import, export, publishing, submission

> Research report, 2026-11-18. Primary sources fetched this session unless marked **[unverified]**. Schema details for Every Eval Ever (EEE) come from the raw `eval.schema.json` and `instance_level_eval.schema.json` at `main` (schema_version `0.3.0`), parsed programmatically.

## 1. Executive recommendation

| Direction | Adopt | Why |
|---|---|---|
| **Export results** | **EEE** (aggregate JSON + `_samples.jsonl`), generated by a new `./bench export --format eee` from our archives. Keep our own tar.gz as the lossless/verifiable form; EEE is the interchange projection. | EEE is the only credible cross-harness results schema with a real shared datastore (HF `evaleval/EEE_datastore`), an instance-level schema that matches our per-item lines closely, and a validator + PR bot. Its gaps (quant, hardware, chat template, system prompt, efficiency) fit through `additional_details` string maps; nothing in our identity model needs to bend. |
| **Import challenges** | **Inspect-style datasets (CSV/JSON/JSONL/HF with `input`/`target`/`choices`/`id`/`metadata`) as the primary ingest shape**, plus **lm-eval task YAML only for `generate_until` + simple metrics**, via a one-shot `./bench import` that emits a native `challenges/*.yaml` with a provenance block. Do not try to execute foreign scorers. | Native challenge YAML is already the canonical identity (`challengeHash` over resolved items). Importing means *transpiling data into our items*, pinning the source dataset revision, and mapping the scorer to one of `exact_match` / `set_match` / `ordered_match` / `constraint` / `code_exec`. Anything needing a model judge, tools, or sandboxes is out of scope. |
| **Publish dataset** | **HF dataset repo**: Parquet (one row per ItemResult, plus a `challenges` config of resolved items), a dataset card with YAML `configs:`, and the auto-generated Croissant JSON-LD HF already serves. Register as an HF *Benchmark* via `eval.yaml` only if our scorers can be expressed (they cannot today; see section 7). Mirror results to EEE datastore separately. | HF is where consumers look; Parquet gives the dataset viewer, `datasets.load_dataset`, and DuckDB for free. Croissant is free from HF and costs nothing to claim. |
| **Do not adopt now** | OpenAI Evals JSONL as a target; Inspect `.eval` as an output; BIG-bench task JSON. | See sections 5 to 6. Cost/benefit is poor for a local-model harness whose unit is (config x challenge). |

Core design constraint carried through every mapping: **the system prompt is config, not challenge.** Every import path therefore strips or refuses a baked-in system message (it becomes a recorded `importedSystemPrompt` note, never part of the item prompt), and every export puts the system prompt in the config-side fields.

## 2. Every Eval Ever (EEE)

Sources: repo `https://github.com/evaleval/every_eval_ever` (MIT); schemas at `every_eval_ever/schemas/eval.schema.json` and `instance_level_eval.schema.json` (both `0.3.0`); `CONTRIBUTING.md`; datastore `https://huggingface.co/datasets/evaleval/EEE_datastore`; paper `https://arxiv.org/abs/2606.14516` (not read in full). README prose mentions "v0.2 release" while schemas say `0.3.0`; no stated migration policy **[unverified: compatibility guarantees]**. A mirror search result suggested 0.2.x numbering; pin to the schema file you validate against and record it.

### Structure and process

- Two files per (model, evaluation run): `data/<collection>/<developer>/<model>/<uuid>.json` (aggregate, `EvaluationLog`) and optional `<uuid>_samples.jsonl` (instance-level, one `InstanceLevelEvaluationLog` per line). The aggregate's `detailed_evaluation_results.{file_path,checksum,hash_algorithm,total_rows}` points at the samples file.
- One aggregate file = one model x one *run* containing N `evaluation_results[]` (one per benchmark/metric). Our grain is one attempt = one config x one challenge, so we emit one aggregate with a single `evaluation_results` entry per attempt, or bundle all of a config's attempts under one file per `invocationId`.
- Validation: `uv run python -m every_eval_ever validate`, exit 0 clean / 1 errors / 2 warnings (warnings block merge). Cross-file checks: matching UUID/folder, `evaluation_id`, `model_id`, row count. A PR bot revalidates on HF PRs; `/eee validate changed` triggers it. Review by an EvalEval member; a `[Submission]` PR-title prefix. The README makes **no claim that scores themselves are verified**, only that records conform.
- Converters (`every_eval_ever/converters/`): Inspect AI (reads `.eval`/`.json`; samples emitted if present), HELM (always samples), lm-eval-harness (`--include_samples`). CLI: `every_eval_ever convert {inspect|helm|lm_eval} --log_path ...`. No converter reads our archives, so we write one; the converter READMEs are the style guide.
- Strictness: top-level and `$defs` objects set `additionalProperties: false`; `generation_args` is also closed. Free-form extension exists only through `additional_details` maps (**all values must be strings**), present on `source_metadata`, `eval_library`, `model_info`, `metric_config`, `score_details`, `generation_config`, `detailed_evaluation_results`, performance, and `source_data`. Instance `metadata` is an object with string values.

### Aggregate (`eval.schema.json`) field map

| EEE field | Our source | Fit |
|---|---|---|
| `schema_version`* | constant from `every_eval_ever.helpers.SCHEMA_VERSION` | exact |
| `evaluation_id`* (`eval_name/model_id/retrieved_timestamp`) | `challengeId/artifact/finishedAt`; append `configHash` to disambiguate configs of one model | fits; the spec'd format has no config slot, so uniqueness for two configs of one model rests on our suffix **(risk: dedupe collisions in datastore)** |
| `evaluation_timestamp`, `retrieved_timestamp`* | `startedAt` / `finishedAt` / export time | exact |
| `source_metadata.source_type`* | `evaluation_run` (raw per-item outputs) | exact |
| `source_metadata.source_organization_name`* , `_url` | `submitter` handle (public), URL of submitter's repo if any | fits; handle is not an "organization" but the field is a free string |
| `source_metadata.evaluator_relationship`* | `third_party` for external submitters, `first_party` only for the model's developer | exact; our `submitter` has no relationship concept, needs a CLI flag |
| `source_metadata.additional_details` | `invocationId`, `hardwareId`, `benchmarkGitSha`, `attemptId`, `interrupted=false` | extension (strings) |
| `eval_library`* `{name,version}` | `{name: "llms-bench", version: env.benchmarkGitSha}` | fits; git SHA as version, since we do not version releases here |
| `model_info.id`* (HF format) | `artifact` (HF repo/path) | fits when artifact is an HF repo; local paths need a rule |
| `model_info.name`*, `developer` | `configId` or artifact basename; developer from repo prefix | fits |
| `model_info.inference_engine {name,version}` | `{runtime, env.runtimeVersion}` | **exact**, the one place a runtime is first-class |
| `model_info.inference_platform` | omit (local) | n/a |
| `model_info.additional_details`* (`deployment_type`, `model_availability` required) | `self_deployed`, `open_weights`; **plus** `quant`, `configHash`, `chatTemplate`, `chatTemplateSha`, `ctxSize`, `serverFlags` as strings | **quant has no first-class field**; carried as `additional_details.quant`. Consumers that group by `model_info.id` will merge Q4 and Q8 runs unless they read it **(biggest comparability hazard; see open questions)** |
| `evaluation_results[].evaluation_name`* | `challengeId` (+ `challengeVersion`) | fits |
| `evaluation_results[].source_data`* | `source_data_private` (`dataset_name`, `additional_details: {challengeHash, challengeVersion}`) or `source_data_hf` once published | fits; `hf_split`, `sample_ids` map to our items |
| `metric_config` | `metric_id: pass_rate`, `metric_kind: pass_rate`, `metric_unit: proportion`, `lower_is_better:false`, `score_type: continuous`, `min 0 max 1`, `metric_parameters:{k: samples}` | exact; our aggregate is "fraction of items scoring exactly 1" and must be named so (binary pass semantics, SCORING.md "Why binary score===1") |
| `score_details.score`* | `aggregate.score` | exact |
| `score_details.uncertainty` | Wilson/bootstrap interval from SCORING.md uncertainty; `num_samples` = item count | **fits well** (standard_error, confidence_interval with `method`) |
| `score_details.details` | `passed`, `retiredItems` count, `staleScoreItems` count, `lines.generated/replayed`, mean `generationTps` | extension |
| `generation_config.generation_args.{temperature,top_p,top_k,max_tokens}` | same | exact |
| `generation_args.prompt_template` | **do not use for system prompt**; leave empty | n/a |
| `generation_config.additional_details` | `min_p`, `presence_penalty`, `repetition_penalty`, `repetition_context_size`, `chatTemplateKwargs` (JSON string), `seed` policy, **`system_prompt_key`, `system_prompt_sha`** | `generation_args` is closed (no `min_p`, no system prompt field), so these go in `generation_config.additional_details`; this is where the system prompt lives, on the config side, preserving our principle |
| `detailed_evaluation_results` | samples file path, `checksum` (sha256), `total_rows` | exact |
| (none) hardware | `env.hardware` + `hardwareId` | **lost as first-class**; `source_metadata.additional_details.hardware` (JSON string) + `hardwareId` |
| (none) efficiency, memory | `peakMemoryGb`, mean tps, wall time | **lost as first-class**; `score_details.details` or a second `evaluation_results` entry with `metric_id: generation_tps` |
| (none) identity hashes | `promptHash`, `scorerHash`, `itemHash`, `challengeHash` | strings in `additional_details`; EEE's own `sample_hash` is a different preimage (see below) |
| (none) errata/release-baseline | ERRATA.md state | `source_data.additional_details.errata_level` string; otherwise lost |

### Instance level (`instance_level_eval.schema.json`) field map

| EEE field | Our source | Fit |
|---|---|---|
| `evaluation_id`*, `model_id`*, `evaluation_name`*, `evaluation_result_id` | from aggregate | exact |
| `sample_id`* | `itemId` (+ `#sample` when `sample>0`) | fits; EEE has **no sample index**, so repeated samples need a `sample_id` suffix or `metadata.sample` |
| `sample_hash` (hash of `input.raw + input.reference`) | recompute from our prompt/expected; keep our `itemHash` in `metadata` | EEE's hash excludes the system prompt and scorer; ours includes both. Do not conflate |
| `interaction_type`* | `single_turn`; `multi_turn` for `parentItemId` items | fits |
| `input.raw`* | prompt text from `content/prompts/<promptHash>.txt` (single-shot) | exact |
| `input.formatted` | the fully templated string, if we capture it **[we do not today; llama-server applies the template]** | lost; could store only the messages array |
| `input.reference`* | scorer `expected` / set / ordered list; for `constraint` and `code_exec` the "reference" is a rule or test file | exact for exact/set/ordered; **lossy for constraint/code_exec** (stringified scorer config, pointing at `scorerHash`) |
| `input.choices` | none | n/a |
| `output.raw[]`, `output.reasoning_trace[]` | `rawOutput` or `output`, and `reasoning` | exact; EEE splits answer vs reasoning like us |
| `messages[]` (`turn_idx`, `role`, `content`, `reasoning_trace`) | for multi-turn: gold history + prompt + model answer, with system message included in `messages[0]` | fits; **gold-history semantics** (earlier assistant turns are gold, not the model's) must be flagged in `metadata.history=gold` since EEE assumes a real transcript |
| `answer_attribution[]`* (`extracted_value`, `extraction_method`, `is_terminal`) | our `extract` regex and cleaned `output` | exact: `extraction_method: regex`, value = extracted string |
| `evaluation.score`*, `is_correct`* | `score`; `is_correct = (score === 1)` | fits; **partial credit** lives in `score`, near-miss and `failureKind` go to `metadata` |
| `token_usage {input_tokens,output_tokens,total_tokens,reasoning_tokens}` | `promptTokens`, `generationTokens` | exact; `reasoning_tokens` unknown unless tokenized |
| `performance {latency_ms, time_to_first_token_ms, generation_time_ms, additional_details}` | `wallTimeSec*1000`; `promptTps`, `generationTps`, `peakMemoryGb` in `additional_details` | fits; no TTFT |
| `error` | `error` | exact |
| `metadata` (string values) | `failureKind`, `nearMiss`, `scoreDetails`, `stopReason`, `seed`, `category`, `tier`, `tags`, `promptHash`, `scorerHash`, `cachedFrom.attemptId` | extension |

Net: EEE carries our results with **no loss of per-item content**, and loses quant/hardware/chat-template/system-prompt/efficiency only as *first-class queryable fields*, retaining them as strings. The risk is not data loss but **consumers ignoring `additional_details`**. Mitigation: encode quant in `model_info.name` (e.g. `Qwen3-32B-Q4_K_M@llamacpp`) while keeping `id` as the HF repo.

### Extension and contribution path

Because validator warnings block merge and the schema is closed, first-class `quantization`/`hardware` requires a schema PR (a "needs a human" lane in CONTRIBUTING.md; agree the approach in an issue first). Proposing `model_info.quantization` and a `hardware` block is a reasonable upstream contribution once we have an exporter producing valid data.

## 3. Inspect (AISI)

Sources: `https://inspect.aisi.org.uk/eval-logs.html`, `.../datasets.html`; `https://github.com/UKGovernmentBEIS/inspect_evals`, `TASK_VERSIONING.md`.

- **`.eval` log**: a binary (zip directory) format, default since Inspect v0.3.46, ~1/8 the size of JSON, incremental sample access; `.json` is the plain alternative. `EvalLog` fields: `version` (currently 2), `status`, `eval` (EvalSpec), `plan`, `results`, `stats` (model usage), `samples[]` (`id`, `epoch`, input, output, target, scores with edit `history`, `events`), `reductions`. `inspect log schema` prints the JSON schema; `inspect log convert`/`dump` for conversion.
- **Verdict as output**: not recommended. It encodes agent/solver/event semantics we lack, and requires synthesizing `EvalSpec`/`plan`. EEE's Inspect converter is the better bridge (we export EEE, and EEE-consumers who want Inspect can still view the logs elsewhere). A `.eval` writer would only be worth it for the Inspect viewer UI **(optional later)**.
- **Dataset/Sample format (import)**: `Sample{input (string or ChatMessage list), choices, target, id, metadata, sandbox, files, setup}`; loaders for CSV/JSON/JSONL/HF; `FieldSpec` maps columns. This is the most practical ingest shape: a flat record with input and target, optional chat-message input for multi-turn, free-form metadata.
- **Task versioning** (`inspect_evals`): `version: "N-X"`, N bumps when results are no longer comparable (scoring, dataset, prompt, parameter changes), X for interface changes; neither decreases; README changelog per bump. This is the closest external analogue to our `challengeVersion` + errata and is worth citing in our docs; our `challengeHash` is strictly stronger (content-derived).
- `inspect_evals` accepts PRs only from pre-approved contributors (`APPROVED_CONTRIBUTORS.md`), a human-gating model, not a verification one.

| Inspect Sample | Our item |
|---|---|
| `id` | `name` |
| `input` (string) | `prompt` |
| `input` (message list) | `turns:` (gold-history) **only if** the assistant messages are intended gold history; a leading `system` message is **stripped to a note** |
| `target` | `expected` / set / ordered list |
| `choices` | fold into prompt text (A/B/C) and `exact_match` with `extract` |
| `metadata` | `tags` / `category` |
| `sandbox`/`files`/`setup` | unsupported (reject) |

## 4. lm-evaluation-harness (EleutherAI)

Sources: `docs/task_guide.md`, `docs/interface.md` in `https://github.com/EleutherAI/lm-evaluation-harness`. The task guide page was fetched; **results JSON nesting is not documented there**, so the output-field list below beyond `results/configs/versions/n-shot/model_args/git_hash/task_hashes` and a chat-template hash is from memory **[unverified]**.

- **Task YAML**: `task`, `dataset_path`/`dataset_name` (HF), `output_type` (`generate_until` | `loglikelihood` | `loglikelihood_rolling` | `multiple_choice`), Jinja `doc_to_text`/`doc_to_target`/`doc_to_choice`, `metric_list` (aggregation, `higher_is_better`), `filter_list` (regex, take_first, majority_vote...), `generation_kwargs`, few-shot config, `metadata.version`.
- **Output JSON**: `results`, `configs`, `versions`, `n-shot`, `config` (model_args, git_hash, `task_hashes`, chat-template hash), per-sample JSONL with `--log_samples`. Task `version` bumps are manual (same idea as Inspect N).
- **Importability**: only `generate_until` tasks are meaningful; `loglikelihood`/`multiple_choice` score by token probability, which our chat-completions harness cannot reproduce, so they are **non-importable** (or importable only as "pick the letter" generation tasks, which is a different task and must be a new challenge id). Jinja templates must be rendered offline per document at import time (requires Python + `datasets`, run by the author script, not by the harness at runtime). Few-shot becomes either baked-in prompt text (changes `promptHash`, fine) or gold-history `turns:` if `fewshot_as_multiturn` was used.
- **As an output target**: lm-eval's JSON is a de facto consumed format, but EEE's `convert lm_eval` exists, so emitting lm-eval JSON adds nothing.

| lm-eval | Ours |
|---|---|
| `doc_to_text` rendered | `prompt` |
| `doc_to_target` | `expected` |
| `filter_list` regex take_first | `extract` |
| metric `exact_match` (with `ignore_case` etc.) | `exact_match` (+ normalization options we already expose) |
| `acc`, `acc_norm`, `perplexity`, `bleu`, `rouge` | not importable (no matching scorer) |

## 5. Hugging Face: datasets, Community Evals, Croissant

Sources: `https://huggingface.co/docs/hub/eval-results`, `.../datasets-cards`, `https://github.com/mlcommons/croissant`, `https://docs.mlcommons.org/croissant/docs/croissant-spec-1.1.html`.

- **Dataset card + Parquet**: `README.md` with YAML (`license`, `task_categories`, `tags`, `configs` with `data_files`, `dataset_info` features). The Hub auto-converts to Parquet and serves a dataset viewer. For us: configs `items` (resolved challenge items: `challengeId`, `challengeVersion`, `challengeHash`, `itemId`, `promptHash`, prompt text, scorer JSON, `category`, `tier`, `tags`), `attempts` (flattened manifests), `results` (one row per ItemResult, with `hardwareId`, `configHash`, quant, runtime as columns). Dataset-side tags `harbor`, `rl-environment` exist for task-directory datasets; not needed.
- **Croissant**: spec 1.1 (MLCommons); HF serves auto-generated JSON-LD at `https://huggingface.co/api/datasets/<repo>/croissant` and embeds it in dataset pages; validate with `mlcroissant`. A Croissant-RAI extension exists but I could not fetch a spec page for it **[unverified]**; recommended action is to add the RAI fields (data collection, limitations, bias) by hand in the dataset card and add to Croissant only if the card tooling supports it. Net: Croissant is a free by-product of Parquet-on-HF, not a format we author.
- **HF Community Evals (`.eval_results/*.yaml`)**: model-repo YAML, each entry `{dataset: {id, task_id, revision}, value, verifyToken?, date?, source: {url,name,user}, notes}`. Benchmarks register through an `eval.yaml` in the dataset repo (`name`, `description`, `evaluation_framework`, `tasks[]{id, config, split, field_spec, solvers, scorers}`; `inspect-ai` is one framework value, the list is maintained in `huggingface.js` `eval.ts`). Badges: **verified** only when `verifyToken` valid (run in HF Jobs with inspect-ai), **community** for open PRs. The feature is marked work-in-progress, beta allow-list.
  - Fit: a result is a single `value` per (model, benchmark task); no quant, runtime, hardware, or system prompt fields, only free-text `notes`. We could emit one `.eval_results` entry per (model repo, challenge) with `notes: "Q4_K_M, llama.cpp, <hardwareId>, system=<key>, configHash=<h>"` and `source.url` pointing at our dataset repo. This gets visibility on model pages cheaply but cannot be "verified" (HF Jobs + inspect-ai only). Our challenge suites cannot be registered as an HF Benchmark without an `evaluation_framework` that matches our scorers.

## 7. Importing as challenge sets: hashing and errata implications

- **Scorer mapping.** Single-answer string/number targets map to `exact_match` (+ `extract` regex). Unordered target lists map to `set_match`; ordered lists to `ordered_match`. Format/structure checks map to `constraint` (including `json_matches`). Code with unit tests maps to `code_exec` (HumanEval/MBPP-style: prompt + test harness; the submission mode must match). Multiple-choice becomes exact_match on a letter with an explicit prompt contract. Everything else (LLM judge, log-likelihood, BLEU/ROUGE, tool use, sandboxes) is rejected with a typed reason in the import report.
- **Generated, not hand-edited.** Per project memory, `trust/economics/financial` YAML come from `scripts/author/draft.ts`; imported YAML follows the same rule: emitted by `scripts/import/<source>.ts`, with the source (dataset repo, revision SHA, split, filter, converter version) written in a header block so the import is reproducible and the YAML is never hand-edited.
- **Identity.** `challengeHash` already covers resolved items (`promptHash:scorer`), so a changed upstream dataset yields a new hash automatically, but only if the import pins the upstream revision; an unpinned `datasets.load_dataset` silently changes hashes. Pin the revision SHA and fail the import if it drifts. A scorer-only fix is an erratum with `score --corpus` re-stamping as already implemented.
- **System prompt.** Importers drop any dataset-embedded system message, record it as import metadata, and warn. This is the one rule that must not be negotiable.
- **Few-shot and chat shape.** Exemplars baked into the prompt are part of `promptHash` (acceptable but deliberate); gold-history `turns:` is the right shape only when the source is already a conversation with assistant messages meant as context.
- **Licensing and contamination.** Each import carries upstream license and citation into the challenge header and into the published dataset card; some benchmark licenses forbid redistribution of items **[needs per-dataset check]**.
- **Tier.** Imported items have no concept difficulty tier; default `tier: unassigned` rather than guessing (tiers reflect concept difficulty per project memory).

## 8. Submission and trust

### How others do it

| Venue | Mechanism | Verification |
|---|---|---|
| EEE datastore | HF PR (`[Submission]`) or drag-drop upload; `/eee validate changed`; EvalEval member merges | Schema/cross-file validation only; scores not re-run (README) |
| HF Community Evals | PR to model repo adds `.eval_results/*.yaml`; shows "community" while open; model author can close; benchmark maintainers can hide a model | `verifyToken` verified badge only if run inside HF Jobs with inspect-ai |
| Terminal-Bench / Harbor | Harbor CLI upload (`terminal-bench-2-1`), validated then pending admin review; older route is an HF PR with a bot; community submissions to TB 2.1 currently closed per the repo (search summary, **unverified** exact status) | Trial results complete, ATIF trajectory required for every passing trial, an agent judge scans passing trials for reward hacking (penalty = reward 0), static misconfiguration checks, community review; cheating submissions removed (`https://www.tbench.ai/news/leaderboard-integrity-update`) |
| inspect_evals | pre-approved contributors only; logs uploaded for issue reports | human gating |

LMArena and the HF Open LLM Leaderboard submission flows were not fetched **[unverified]**.

Pattern: nobody verifies by *independent hardware re-execution*. Credible venues verify by (a) full transcripts so a reviewer or judge can audit, (b) schema/completeness checks, (c) human review, and (d) in HF's one cryptographic case, running inside platform-controlled compute.

### What our archives already enable

- **Offline re-score of submitted outputs.** Each attempt `.jsonl` plus `content/` is self-sufficient: `bench score` can re-apply the scorer named by `scorerHash` to the submitted `output` and reject any line whose score disagrees. This catches score tampering and scorer drift cheaply, with no model access.
- **Prompt identity checks.** `promptHash` / `itemHash` / `challengeHash` / `configHash` recomputed from the bundled blobs must equal the header and line values, and the `challengeHash` must equal the maintainer's release baseline for that `challengeId@version` (plus errata state). `bench export` is already self-verifying (tar.gz).
- **Provenance fields**: `hardwareId` (12-hex, OS-independent, no PII), `submitter` (public handle, `@` refused), `invocationId`, `env.benchmarkGitSha`, `lines.generated/replayed` (separates cached replays), schemaVersion 3 gate, per-item `seed`, token/tps/wall/memory.
- **Plausibility checks derivable today** (no new infra): `generationTokens` vs `rawOutput` length ratio; tps vs the claimed hardware's known range; `wallTimeSec` consistent with tokens/tps; all items present, `interrupted: false`, sample counts; outputs that equal other submitters' outputs for the same seed on different hardware.

### What is missing

1. **Authenticity of generation.** An archive records what a model "said", but a submitter can hand-write outputs and recompute valid hashes; offline re-score proves scoring, not that the model produced the text. Options: (a) require the full `rawOutput` plus a **streamed server transcript** (request body and response, with the sampler seed), enabling spot-check re-execution by a maintainer on a sample of items (cost-effective since "resample only edge items"); (b) maintainer re-runs a random subset on trusted hardware and compares outputs statistically (outputs differ across hardware, so compare pass-rate on that subset, not bytes); (c) signed run attestation (Sigstore/cosign-style keyless signing of the tar.gz hash by the submitter's GitHub identity), which proves *who* submitted, not what ran **[design proposal, not an existing standard we verified]**.
2. **Hardware attestation.** `hardwareId` and `env.hardware` are self-reported probes. There is no way to verify a claimed M5 Max. Treat as an unverified claim; downweight efficiency (tps, wall, memory) from unverified hardware, and trust pass/fail only to the degree the sampling checks in (1) hold.
3. **Model-artifact attestation.** `artifact` + `quant` is a string; there is no GGUF/MLX weights hash in `configHash`. Recording the weights file SHA-256 in the manifest would let a re-run check the same weights (cost: hashing a large file once per config; cache by path+mtime).
4. **Signing and tamper evidence.** No signature, no hash chain across lines. A maintainer-side ledger (append-only index of accepted `attemptId` -> archive SHA-256) is enough for dedupe and replay detection without cryptography.
5. **Dedupe.** `attemptId` carries a timestamp, so the same run resubmitted gets a different identity only if re-run; the same file is deduped by `attemptId` already. Add a content-level dedupe key `(configHash, challengeHash, hardwareId, submitter, per-line (itemHash,sample,seed,output hash))` to catch resubmission and cross-submitter copying.
6. **Submission schema pinning.** EEE's `0.3.0` vs `0.2` ambiguity means an exporter should record the exact schema version and validate with the pinned validator in CI.

### Recommended pipeline (simple first)

1. Submitter: `BENCH_SUBMITTER=<handle> ./bench run`, `./bench export` per attempt (existing).
2. Submit by HF dataset PR to our results repo (or a GitHub PR with LFS-less tar.gz under size limit) with an included `submission.yaml` (handle, contact-free, hardware claim, notes).
3. CI (maintainer repo): verify archive self-consistency (existing export verification), recompute all hashes, `challengeHash` equals release baseline, schemaVersion 3, completeness, offline re-score matches stored scores line by line, plausibility checks, dedupe key not seen.
4. Tier status: **unverified** (default, shown with a badge), **spot-checked** (maintainer re-ran a random subset, within tolerance), **maintainer-run**. Mirror the status in the export's EEE `evaluator_relationship` and `source_metadata.additional_details.verification`.
5. On accept: add to the ledger, rebuild `./bench report`, republish Parquet and the EEE mirror.

## 9. Open questions for you

1. **Quantization comparability in EEE.** `model_info.id` is the HF repo and has no quant field. Do you want to propose a schema extension upstream (`quantization`, `hardware`) or live with `additional_details` and a `name`-embedded suffix?
2. **Dataset publishing scope.** Publish item prompts and expected answers publicly (contamination risk), or hold back a private split used only for maintainer verification re-runs? This also determines whether `./bench export --format eee` ships prompts.
3. **Trust tiers.** Is "unverified / spot-checked / maintainer-run" acceptable, or must submissions be re-run before appearing at all? Spot-check cost is real compute on your hardware.
4. **Weights hash.** OK to add a weights-file SHA to the manifest (schema bump to 4 and a `configHash` decision: provenance only, as `ctxSize` is, or part of identity)?
5. **Import priority.** Which external suites do you actually want first? That determines whether the ingest tool starts with Inspect-style JSONL/HF or something source-specific, and whether imported items need a default `tier`.
6. **HF Benchmark registration.** Worth pursuing an HF-supported `evaluation_framework` entry for our scorers (needs upstream work), or skip and publish plainly with a dataset card?
7. **EEE grain.** One aggregate file per attempt, or per `invocationId`? Per-attempt keeps hashes simple; per-invocation matches EEE's one-file-per-model-run convention.
